# 开发总计划 / 离线优先修订

2026-11-01 新指令取代先前“所有业务均未授权”的限制：当前交付 Flutter↔Pikafish 最小通信验证、架构、完善计划；下一轮按离线增量推进。登录后功能及依赖在线服务的能力延期，范围见 OFFLINE_SCOPE.md。

## 顺序与门槛

1. M1 技术基座：固定引擎/NNUE/SDK，验证桌面Process和移动FFI，解决权重分发许可；不要用网页引擎结果代替本地验证。
2. M2 离线领域与文档：先规则和棋树，后棋盘与编辑，再本地草稿和FEN/文本。每个切片独立验证。
3. M3 引擎业务：调度/取消、分析面板、人机对弈、复盘与设置依次接入。
4. M4 离线功能闭环：多格式、导出、棋谱检索、本地错题收藏、体验和可访问性。
5. M5 五平台交付：构建打包、真实设备、资源预算、崩溃恢复、离线首次启动、升级迁移与源码/许可证分发。

估时采用任务粒度和依赖，不承诺未经移动spike校准的日期。每个B项拆成1–3个可验收切片；若单片不能独立验证，先做接口和fixture而非大批生成代码。阶段退出条件见 MILESTONES。

## 风险与应对

- NNUE 限制商用：权重授权或兼容开放权重未解决前不打包发布；不改换引擎却宣称仍为最新版Pikafish。
- 移动C ABI：最小包装、工作线程、coop stop、所有权验证，失败时记录实际平台限制。
- 象棋裁决：合法走法与长将长捉规则分开；规则配置必须记录在棋谱，不能硬映射不存在的UCI选项。
- 弱化棋力：先提供可解释预算，不声称与站点等级等效；对局样本校准后再命名。
- 文件兼容：逐格式授权fixture和语义round-trip，未知格式/损坏输入不覆盖用户草稿。

每个阶段提交记录需求ID、接口、失败模型、验证命令/平台、遗留项、交接。最终离线完成声明必须所有纳入项都通过，未知仍列缺口。
